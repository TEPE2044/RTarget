# 活力值奖罚系统 —— 机制最终版 v2.0

> 本文档只描述机制，不涉及技术框架选型。**所有旧版本（v1.x 的 A/B/C 三节点、惩罚复合体、
> 补做窗口、返还）全部作废**，以本版为准。
>
> v2.0 变更（推倒重来）：一个目标 = **一个奖励 + 一个惩罚**；做到 +S、做不到 −S，
> **一锤子结清**；砍掉 A/B/C 三节点、惩罚复合体、补做窗口、返还；做不到就**退回待办**。

## 一句话

懒人自驱动系统：给一件事押上活力值，到点做到就奖、做不到就罚，一次结清。
- 名称 RTarget

## 核心概念

### 活力值（全局血池）

- 全系统唯一数值，所有存档公用，初始值默认 **10**
- 做到 → 增加；做不到 → 减少
- 四舍五入取整，不留小数

### 存档（周期）

- 存档 = 一段独立历程；活力值全局公用，开新档不清旧债
- 可以开多个档，进行中的档之间随意切换；封档后进入历史
- 封档规则：
  - 有未了结之事 → 扣**当前活力值的 10%**
  - 存档内目标全部了结 → 封档**免费**
- **封档即收口**：档内还没了结的目标一并关闭（不再单独扣分，那 10% 就是代价），
  免得封了档之后它们还在后台继续判负
- **删除已封档的存档**：存档和它的目标一并删除，但**活力值流水保留、分数不变** ——
  否则「封档扣 10% → 把档删了」就成了刷分漏洞。未封档的不能删，先封档。

## 数值表

| 档位 | 分值 |
|---|---|
| 低 | 5 |
| 中 | 10 |
| 高 | 20 |
| ALL IN | 当前活力值 × 80%（四舍五入，最低 1） |

> v2.0 起**不再限制负值时禁用高档 / ALL IN** —— 押多少由自己定，机制不替他把关。

## 时间计算

- **死线 = 一个具体时刻**（精确到分钟），**到点即判负**。
  例：设 8/1 18:00 → 8/1 18:00 一过就算超时。
- 结算是**惰性**的：判定发生在打开应用的那一刻（`settle_goals`），不是后台闹钟。
  所以「到点」和「实际扣分」之间可能有几分钟到几小时的间隔 ——
  但判定用的是死线时刻本身，晚开也不会少扣。

## 目标（唯一实体）

一个目标就是一个单元，设立时确定六件事：

1. **内容**（要做什么）—— 可以从「待办」里挑一条，也可以临时自己写
2. **死线**（具体时刻）
3. **押注档位**（低 / 中 / 高 / ALL IN）→ 落成实际分值 `stake`（写入时快照）
4. **奖励**（做到给什么）—— 可以从「愿望」里挑一个，也可以临时写一句
5. **惩罚**（做不到罚什么）—— 写一句就好，系统的处理是固定的
6. **怎么做**（执行区正文，Markdown，随时可改）

> **内容来源是两件事。** 「从待办挑」/「从愿望挑」只是**怎么挑**的差别，不改变任何机制：
> - 从待办挑的目标，立项后那条待办**移出清单**（taken）
> - 从愿望挑的奖励，目标**达成那一刻**那个愿望被划成已实现
>
> 两个清单都与积分系统无关。待办即使不立项，也可以直接勾掉，不产生任何流水。

### 结算规则（一锤子）

| 结果 | 活力值 | 奖励 | 目标 | 来源待办 |
|---|---|---|---|---|
| **做到** | **+S** | 当场兑现（愿望单里的那个划掉） | 关闭 | 待办**消耗一格** |
| **做不到**（到点未申报 / 主动放弃） | **−S** | 作废 | 关闭 | **退回待办**（次数不动） |

- 没有第二阶段、没有补做窗口、没有返还、没有复合体。
- **主动放弃 = 提前判负**，效果与到点超时完全一致。
- 「做到」以**手动申报**为准；到点没申报就是做不到。

### 打卡型目标（长期目标）

- 目标可以带一个**打卡次数**（立项时设，`check_total`），用来表达"连续 30 天背单词"这类长期目标。
- **`check_total` 为 null 就是普通的一次性目标** —— 现有目标全是这一类，行为一字未变。
- **每天最多打一次**（按**北京日期**算，不是服务器 UTC 日期），打满 `check_total` 次即**自动结算**：
  与「做到」完全相同（+S、奖励兑现、来源待办扣一格），不需要再手点「完成」。
- **到死线没打满 = 判负**，走现有的 `settle_goals`，照旧 −S。「死线必判」这条铁律不破。
- **没打满不许手点「完成」**：否则立完当天点一下就能白拿 S，"打几次"这个承诺等于没有。
  这道门槛在库里（`complete_goal` 里挡），不是只在界面上挡。
- 立项时如果次数要得比"从今天到死线的剩余天数"还多，向导会挡住不让继续 ——
  那种目标从设立那一刻就不可能达成。

### 待办的「次数」（电量格）

- 待办可以带一个**次数**（建的时候设，默认 1，界面上显示成电量格），它只是个计数器，**不参与押注**。
- **每完成一次由它立项的目标，就扣一格**；扣完这条待办就算用完。
- **判负 / 放弃都不扣格** —— 因为"最终没完成"，事情还没了结，退回清单继续躺着。
- 退回时**次数原样不动**：还剩几格就还是几格。

### 待办的「内容」

- 一条待办 = **标题** + **内容**（Markdown，默认空），列表里内容以引用样式挂在标题下面。
- 立项时正文会带进目标的**执行区**（当作起点，之后在目标详情里继续写）。

## 设计原则

- 一切结算以手动申报为准，到点不申报即判负
- 一锤子买卖：**要么做到拿奖励，要么认罚**，不留中间地带 ⇄ 拖延没有第二次机会
- 开新存档是加压不是重开

# 架构决策（v2.0）

- **前端**：Vue3 SPA + **Vant 4**（用户挑定的移动端组件库）+ TypeScript + Vite
- **后端**：Supabase（Postgres + Auth），单一数据真相，天然多端同步
- **结算引擎**：惰性结算——打开应用时对比当前时间与各目标的死线，触发判负；
  **无推送、无倒计时、无后台服务**
- **端形态**：浏览器优先；Capacitor（手机，`vitality-app/app`）/ Tauri v2（桌面，`rtarget-desktop`）为可选套壳，两端**共用同一份前端源码**；因无通知需求，壳退化为纯容器，随时可加可去
- **Expo 淘汰**：React 不熟导致维护风险；**Uniapp 淘汰**：多端优势被 Supabase 同步抵消；**Electron 淘汰 → Tauri**：桌面壳改用 Tauri v2（更轻、官方 updater 仅桌面可用）；**手机端保留 Capacitor**：Tauri 移动端没有官方 OTA，而 OTA 是本项目的刚需

## Auth 决策（v2.0 补充）

- **认证**：Supabase Auth，单人自用。**邮箱 + 密码**；或**邮箱验证码**
  （有密码直接进、没密码才要求设一次，一条流程覆盖注册 / 补密码 / 忘记密码）
- **不做魔法链接 / 深链**：跳回应用要靠自定义 scheme，微信等邮件内置浏览器会拦掉，换谁都躲不开
- 所有数据表经 RLS 隔离（user_id = auth.uid()），注册即送初始 10 分
- 全系统无服务端代码：客户端 + RLS + security definer 函数闭环
