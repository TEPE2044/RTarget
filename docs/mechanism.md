# 活力值奖罚系统 —— 机制最终版 v1.3

> 本文档只描述机制，不涉及技术框架选型。所有旧版本的推测与待定项全部作废，以本版为准。
> v1.1 变更：A 与 C 各自独立死线，惩罚复合体由此获得补做窗口。
> v1.2 变更：**C 死线只能落在 A 死线之后的 1~3 天**，补做窗口最长 3 天。
> v1.3 变更：死线统一为**完成日**语义（当天 24:00 截止，次日 0 点结算），**今天可选**。

## 一句话

懒人自驱动系统：所有事情通过奖罚机制迭代结算，直到零散事情被逐个解开为独立、已了结的单元。
- 名称RTarget

## 核心概念

### 活力值（全局血池）

- 全系统唯一数值，所有存档公用，初始值默认 **10**
- 奖励结算 → 增加；惩罚结算 → 减少
- 穿透负值时 ALL IN 与高档禁用，仅剩中/低可押，直到回正

### 存档（周期）

- 存档 = 一段独立历程；活力值全局公用，开新档不清旧债
- 封档规则：
  - 直接封档（有未了结之事）→ 扣当前活力值的 **10%**
  - 存档内全部走向奖励分支 → 封档**免费**
- **删除已封档的存档**（v1.3 补充）：存档和它的目标一并删除，但**活力值流水保留、分数不变** ——
  否则「封档扣 10% → 把档删了」就成了刷分漏洞。未封档的不能删，先封档。

## 数值表
- 活力值 四舍五入，不要小数点

| 档位 | 分值 |
|---|---|
| 低 | 5 |
| 中 | 10 |
| 高 | 20 |
| ALL IN | 当前活力值 × 80%（赢 原值 + 自身 *0.8 / 输 原值 - 自身 *0.8） |

## 时间计算
- 以日为最小单位，每日凌晨0点结算
- **死线 = 「你要在哪天做完」**（v1.3 澄清）：当天 24:00 截止，判负/结算发生在**次日 0 点**。
  所以**今天是可以选的** —— 今天做完，明天 0 点才判负。
- 实例1：死线 = 9/15（今天做完）→ 9/16 0点结算
- 实例2：死线 = 9/16 → 9/17 0点结算
- **A 与 C 各有独立死线**（v1.1 修订）：设立目标时分别指定，**C 的死线必须晚于 A**。
  从 A 判负那一刻到 C 死线之间的这段，就是惩罚复合体的**补做窗口**。
- **C 死线只能落在 A 死线之后的 1~3 天**（v1.2 收紧）：即补做窗口最长 3 天，不给无限拖。
  设立时是三选一，不能让用户随便填日期。
- 实例3：A 死线 9/15、C 死线 9/16 → 9/16 0点 A 判负并扣分、C 开启；9/17 0点复合体出结果
- 实例4：A 死线 9/15、C 死线 9/18 → 窗口 3 天（可选的最长档）
- 实例5（需求原话）：A 设 8月1日 → C 只能取 **8月2日 / 8月3日 / 8月4日**

> v1.3 修订原因：旧版把存储的 due_at 当成「死线日的 0 点」，于是「死线 = 今天」等于一建立就判负，
> 表单被迫把最小区间卡在明天 —— 但用户想说的是「今天做完」。现在统一为**完成日**语义：
> 库里仍存「次日 0 点」这个判负时刻，展示层退回一天。**无需迁移数据**，存量条目的判负时刻不变。



## 节点与结算规则（最终版）

### 初始节点 A

设立时确定：内容、时限、档位（低/中/高/ALL IN）、绑定的奖励 B 与惩罚 C。

```
初始节点A（死线 = A 死线）
 ├─ 惩罚C：立刻扣分A
 │    └─ 惩罚复合体（A+C）：扣分C   ← 补做窗口 = A 死线 → C 死线
 │         ├─ A+C 未完成 ──► 扣除 A+C 的分
 │         ├─ A完成/C没完成 ──► 无分（不扣不返）
 │         ├─ C完成/A没完成 ──► 无分（不扣不返）
 │         └─ A+C 完成 ──► 返还 A+C 的分（提前了结，不必等 C 死线）
 └─ 奖励B：立刻奖励B
```

### 结算表（惩罚复合体）

| A | C | 结算 |
|---|---|---|
| ✗ | ✗ | 扣 A + C 的分 |
| ✓ | ✗ | 无分（A 的已扣分不再追缴，C 的已扣分不返还） |
| ✗ | ✓ | 无分（同上） |
| ✓ | ✓ | **返还 A + C 的分** |

### 结算时序

1. A 到 A 死线仍未申报 → **立刻扣 A 的押注分**，C 由 bound 开启为 active
2. 进入惩罚复合体（A+C）→ **再扣 C 的分**
3. 复合体出结果（触发条件二选一：**C 到 C 死线**，或 **A、C 都完成则提前结算**）：
   - 都没完成 → 再扣 A + C（第三次扣，叠加）
   - 完成其一 → 无分变动
   - 都完成 → **返还 A + C 的分**（把之前扣的全返）

> v1.1 修订原因：旧版 C 继承 A 的死线，A 一判负 C 就已过期，复合体在同一次结算里
> 直接走完"都没完成"，且"完成其一"分支不关闭 C —— 结果两边按钮点了没反应、
> 流程永不结束，只能放弃。现在 C 有独立死线，窗口成立。

### 奖励分支（B 的完整生命周期）

- **设立**：B 与 C 同为用户设立 A 时预绑的内容
- **开启**：A 达成 → B 立刻解锁（"立刻奖励"指开启资格，非立刻加分）
- **结算**：先加分，保留确认按钮，直到点击确认，无时间限制
- 奖励和惩罚分支自身无**档位**，继承原目标；
- 无倒计时推送，一切以用户打开应用时的主动申报为准

## 设计原则

- 一切结算以手动申报为准，超时不申报即判负
- 惩罚复合体把原目标和拖延之事捆绑：只有全部做回来，才能拿回全部扣分
- 半途而废（只完成一半）比不做更"好"：做了不返还，不做还要再扣——**要么全做，要么别碰**？〔做完就返还，做一半不继续扣，没做完就继续扣啊，这怎么会亏？）
- 开新存档是加压不是重开

# 架构决策（v1.0）

- **前端**：Vue3 SPA（用户主力技术栈）
- **后端**：Supabase（Postgres + Auth），单一数据真相，天然多端同步
- **结算引擎**：惰性结算——打开应用时对比当前时间与各节点时限，触发判负/返还；**无推送、无倒计时、无后台服务**，界面至多显示当前时间
- **端形态**：浏览器优先；Capacitor（手机）/Electron（桌面）为可选套壳，因无通知需求，壳退化为纯容器，随时可加可去
- **Expo 淘汰**：React 不熟导致维护风险；**Uniapp 淘汰**：多端优势被 Supabase 同步抵消；**Electron 降级为可选**：无通知引擎需求后，"重"不再是阻塞项

## Auth 决策（v1.0 补充）

- **认证**：Supabase Auth，单人自用 → **魔法链接（email OTP）**形态，零密码维护
- 所有数据表经 RLS 隔离（user_id = auth.uid()），注册即触发 `grant_initial_vitality` 送初始 10 分
- 全系统无服务端代码：客户端 + RLS + security definer 函数闭环
